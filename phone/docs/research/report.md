# Write our own Kotlin SIP stack, borrow everything else

Nobody ships a permissively licensed, native Kotlin (or Swift) SIP-over-WebSocket user agent that runs on iOS, so the realistic path is to keep growing our own KMP SIP core and model its structure on sip.js's MIT `core/`. We would copy selected MIT pieces from uvp-gb28181-sim and webphone-android, and run media on webrtc-kmp (Apache-2.0, libwebrtc). This is the same engine our browser phone already uses, so FreeSWITCH interop mostly comes down to sending the same SDP sip.js sends. Everything around the SIP engine already exists under permissive licences and can be borrowed: the Android Core-Telecom call layer, Telnyx's MIT call-service and push structure, and the FCM/PushKit wake-up pattern. The parts nobody can give us are the transaction and dialog state machines, and a server-side "push, park, wait for re-REGISTER, bridge" flow. FreeSWITCH has no built-in support for that flow, so we would add it in our own Lua routing. Our core works today as a registration-only prototype: JVM-only, 17 tests. Several defects Codex flagged are already fixed in the current code, but there is no INVITE, dialog, refresh or incoming-request handling yet. The bounded scope is roughly 5–7k Kotlin lines for a sip.js-equivalent subset, or about 2–3k for a single-dialog first call. The safest proof order puts a bare two-way-audio call on a physical Android phone before any UI, push or iOS work.

## No permissive Kotlin SIP-over-WSS library exists, but good parts do

The inventory is clear. No mature, MIT/Apache/BSD SIP UA covers Kotlin Multiplatform with iOS. The well-known stacks are either copyleft or dead: Sipdroid, mjSIP and Lumicall are GPL, CSipSimple is copyleft and last pushed in 2016, RestComm's Android SDK is AGPL, Linphone is GPL/AGPL and PJSIP is GPL ([Sipdroid](https://github.com/i-p-tel/sipdroid), [mjSIP](https://github.com/haumacher/mjSIP), [restcomm-android-sdk](https://github.com/RestComm/restcomm-android-sdk), [linphone-android](https://github.com/BelledonneCommunications/linphone-android), [pjproject](https://github.com/pjsip/pjproject)). The only mature permissive Java stack is **NIST JAIN-SIP**, a public-domain notice with full transactions and dialogs ([usnistgov/jsip](https://github.com/usnistgov/jsip)). It is JVM-only, its last Maven artifact dates from 2018 ([Maven Central](https://search.maven.org/search?q=g:javax.sip)), and its WebSocket client is a hack. Reading the code shows it sends a hardcoded RFC 6455 sample `Sec-WebSocket-Key` and then calls `Thread.sleep(500)` instead of waiting for the 101 response ([NioWebSocketMessageChannel.java](https://github.com/usnistgov/jsip/blob/master/src/gov/nist/javax/sip/stack/NioWebSocketMessageChannel.java)). RestComm, which built a WebRTC SDK on JAIN-SIP, left `transport = "wss"` commented out ([JainSipClient.java](https://github.com/RestComm/restcomm-android-sdk/blob/master/restcomm.android.sdk/src/main/java/org/restcomm/android/sdk/SignalingClient/JainSipClient/JainSipClient.java)). Searches for a Kotlin or Swift RFC 7118 UA library turned up only JS stacks, a React Native JsSIP fork and a .NET project ([react-native-jssip](https://github.com/avodevelopment/react-native-jssip), [sip-over-websocket](https://github.com/andikatjacobdennis/sip-over-websocket)).

What does exist is a set of small, permissively licensed Kotlin pieces that each solve part of the problem:

| Source | Licence | What it is worth to us | What to avoid |
|---|---|---|---|
| **Our core** (`phone/sip`) | ours | Ktor WSS transport, digest, bounded 401/407 and 423 REGISTER retries, 17 tests | Android and iOS targets since 2026-11-18; no dialogs, refresh, reconnect or inbound requests |
| **sip.js** `core/` | MIT | The blueprint: transactions, dialogs, UAC/UAS, user-agent core (~4k TS NCLOC) | Grammar is pegjs-generated; rewrite it by hand |
| **uvp-gb28181-sim** `shared/sip` | MIT | KMP byte-based parser/serializer, `SipMessage`, pure-Kotlin MD5 with RFC vectors, response builders, `SipTransport` + `Flow` interface, test style | Camera SDP, GB28181 domain (~60%), no transaction layer, flawed CANCEL handling |
| **webphone-android** | MIT | ~870-line `SipEngine` over OkHttp WSS aimed at FreeSWITCH: REGISTER, INVITE, hold, BYE, DTMF, REFER; ~1,070 test lines | Android-only; README says the flows are not yet exercised against a live WSS gateway |
| **nwaycn/nsbc** Android SDK | Apache-2.0 | Another Kotlin WSS SIP engine (SipEngine, SipTransport, DigestAuth) | Not inspected in depth |
| **JAIN-SIP** | NIST notice | Reference for RFC 3261 edge cases | Not KMP, broken WS client |

The uvp-gb28181-sim code is high quality for a month-old project: MIT, KMP across Android, iOS and JVM, and 307 `@Test` methods in its `sip/` tests alone ([uvp-gb28181-sim](https://github.com/Frank-Coding97/uvp-gb28181-sim)). But it is a camera-device simulator. It has no RFC 3261 §17 transaction layer (its `SipOutbox` says so explicitly), no WS or TLS transport, MD5-only digest, and SDP with GB-specific `y=`/`f=` lines and no ICE or DTLS ([SipOutbox/Sdp in shared/sip](https://github.com/Frank-Coding97/uvp-gb28181-sim/tree/main/shared/src/commonMain/kotlin/com/uvp/sim/sip)). The Codex code review ([codex_uvp_review.md](notes/codex_uvp_review.md)) finds real defects. Its digest picks the first qop but always hashes method and URI, so `auth-int` comes out wrong. Unlisted headers are case-sensitive. Dedup swallows retransmitted requests without replaying the response. And a CANCEL destroys a post-200, pre-ACK dialog, behaviour a test even endorses. Codex's verdict matches the research notes: lift `SipMessage`, the parser, serializer and header files (after fixes) and the response builders, and keep our own digest. webphone-android is the closest functional match, but its own README marks REGISTER, INVITE and DTMF as "not yet exercised against the stack's WSS gateway" and incoming INVITE as "explicitly UNTESTED" ([webphone-android](https://github.com/LarsArtmann/webphone-android)). Read it for FreeSWITCH lessons, not as proven code. One example: its source notes that the colon form of DTMF INFO "is 200-OK'd by FreeSWITCH and silently dropped".

Our own core needs a careful read, because the review evidence and the current code disagree. The Codex core review ([codex_own_sip_core_review.md](notes/codex_own_sip_core_review.md)) flagged binary WebSocket frames being discarded, 423 being refused, a password-bearing `toString()`, and unsupported qop being silently downgraded. **In the current source (read 2026-11-18) all four are fixed.** `SipClient.kt` decodes `Frame.Binary` and retries once on 423 using `Min-Expires`. `SipAccount.toString()` redacts the password. `Digest.kt` throws on any qop other than `auth` instead of downgrading. The Codex plan review ([codex_plan_review.md](notes/codex_plan_review.md)) also confirms the 423 and bounded-retry handling. Fixed since (2026-11-18): a closed connection now fails waiting requests, REGISTERs are serialised, responses are matched by Via branch, Content-Length is honoured, our own binding is picked among several Contacts, and the client tests check the digest independently. The module now declares Android and iOS targets (JetBrains' layout, `sip`/`shared`/`androidApp`); Android builds, iOS needs a Mac and has not been built. Still open: messages that arrive with no listener are dropped (needs the dispatcher for incoming requests), and renewal and reconnect are not built.

How much SIP do we actually need? Measured on sip.js, a phone that does REGISTER, INVITE in both directions, CANCEL, BYE, ACK, digest and DTMF needs about **8–9k TypeScript NCLOC** out of 13,384. That is ~4k in `core/`, ~3k in the API layer and ~1.1k for transport plus the session-description handler. The researchers estimate it shrinks to about 5–7k Kotlin lines ([onsip/SIP.js](https://github.com/onsip/SIP.js)). Over WSS the hardest RFC 3261 timers are mostly inert: retransmission timers A/E/G do not apply on reliable transports ([RFC 7118](https://www.rfc-editor.org/rfc/rfc7118.html)). Timer B/F deadlines, 2xx/ACK handling and CANCEL races still matter. A single-dialog state machine (~2–3k lines) is enough for a first call. sip.js's layering is what keeps re-INVITE, glare and CANCEL/200 races tractable later, so the core should be shaped to grow into that layering rather than rewritten.

## Copying sip.js's SDP behaviour makes FreeSWITCH interop a non-event

**webrtc-kmp is the only real KMP wrapper over libwebrtc.** It is Apache-2.0 and supports Android, iOS and JS. It pins WebRTC **M125**: `io.github.webrtc-sdk:android:125.6422.06.1` on Android and WebRTC-SDK `125.6422.07` on iOS ([libs.versions.toml](https://raw.githubusercontent.com/shepeliev/webrtc-kmp/main/gradle/libs.versions.toml)). It has a common `DtmfSender`, so RFC 4733 DTMF works from shared code ([shepeliev/webrtc-kmp](https://github.com/shepeliev/webrtc-kmp)). The project is quiet. GitHub API metadata dates the latest release, v0.125.11, to **2025-09-07**, with no default-branch commits since, and every release is marked pre-release ([releases](https://github.com/shepeliev/webrtc-kmp/releases)). One research note guessed Sep 2026 from a release page that showed no year; the API date wins. Of its 14 open issues, only one concerns audio. The iOS ones are a use-after-scope bug that garbles camera formats, a request to move from CocoaPods to SwiftPM, and old pod-build failures ([issues](https://github.com/shepeliev/webrtc-kmp/issues)). For an audio-only phone, M125 is functionally sufficient, because Opus, G.711, DTLS-SRTP, rtcp-mux and BUNDLE have been stable for years. The cost is missing security patches and audio-device fixes. The fallback is cheap and well defined: fork webrtc-kmp and bump it to webrtc-sdk/android 137.x ([webrtc-sdk/android](https://github.com/webrtc-sdk/android)) and stasel's iOS XCFramework ([stasel/WebRTC](https://github.com/stasel/WebRTC/releases)), or write a ~500-line expect/actual wrapper over just PeerConnection, audio tracks and SDP (an estimate). Google's own Android WebRTC artifact is unmaintained; stream-webrtc-android and webrtc-sdk/android replace it ([GetStream/webrtc-android](https://github.com/GetStream/webrtc-android)).

The interop recipe follows from what sip.js actually does, verified in its source. **sip.js applies no SDP modifiers by default and does not trickle.** `getDescription()` waits for ICE gathering to finish, capped at **5000 ms** by the default factory, and then sends the full local description ([session-description-handler.ts](https://raw.githubusercontent.com/onsip/SIP.js/main/src/platform/web/session-description-handler/session-description-handler.ts), [factory-default](https://raw.githubusercontent.com/onsip/SIP.js/main/src/platform/web/session-description-handler/session-description-handler-factory-default.ts)). Hold is a re-INVITE that flips the direction: sendrecv becomes sendonly, and recvonly becomes inactive. Codex confirmed that our browser phone passes no modifiers either ([codex_plan_review.md](notes/codex_plan_review.md)). On the server side, FreeSWITCH turns on DTLS-SRTP automatically when an offer carries `a=fingerprint`. It is a full ICE agent by default, processes **only UDP candidates**, generates no relay candidates and has **no TURN client**. It does accept client relay candidates and falls back to them when `apply-candidate-acl` drops everything else ([FreeSWITCH docs: WebRTC over SIP](https://developer.signalwire.com/freeswitch/users-and-endpoints/webrtc-sip/)). A FreeSWITCH maintainer answered "No" when asked whether trickle ICE works through mod_sofia ([freeswitch-users 2020-12](https://lists.freeswitch.org/pipermail/freeswitch-users/2020-December/134315.html)). So non-trickle is mandatory, not a simplification.

The native phone should therefore do exactly what the browser does. Set the local description, wait for gathering with a deadline (sip.js uses 5 s; 1–2 s with early release after the first srflx is the researchers' suggestion), and send the full `localDescription` unmodified in the INVITE or 200. Use Unified Plan with one audio transceiver and `rtcpMuxPolicy=require`. Answer FreeSWITCH re-INVITEs on the same PeerConnection. The deadline is not cosmetic: sip.js users report the INVITE being held for the whole timeout when an srflx or relay server never answers ([sip_js group](https://groups.google.com/g/sip_js/c/Lt6KhYqDdUc)). The documented native↔FreeSWITCH failures are generic rather than native-specific. One is `setRemoteDescription` failing with "SDP without DTLS fingerprint" when FreeSWITCH sends non-WebRTC SDP on a call *to* the phone ([freeswitch-users 2015-03](https://lists.freeswitch.org/pipermail/freeswitch-users/2015-March/111726.html)). Another is a 488 from a codec mismatch; dart-sip-ua's FAQ lists both for FreeSWITCH users ([dart-sip-ua](https://github.com/flutter-webrtc/dart-sip-ua)). A 2021 report claims FreeSWITCH sends STUN checks only to the first candidate ([freeswitch-users 2021-08](https://lists.freeswitch.org/pipermail/freeswitch-users/2021-August/134932.html)). That is unanswered and unconfirmed, but cheap to guard against by not leading with an unreachable host candidate. FreeSWITCH normally sits on a public IP, so a phone behind carrier NAT usually connects via srflx or peer-reflexive candidates. A STUN server is advisable and TURN (UDP plus TLS/443) is insurance for restrictive networks. Nobody has measured how often mobile carriers actually need TURN against a public-IP FreeSWITCH. Two things are also unverified and need a lab test: whether FreeSWITCH accepts an ICE restart in a re-INVITE (needed for Wi-Fi↔LTE handover), and whether `a=extmap-allow-mixed` causes trouble (no confirmed failure found).

## Every production softphone has four layers, and we can borrow two

Across vendors the structure is the same: a signalling engine, a libwebrtc peer connection, a platform call manager (Telecom or CallKit), and a push path that wakes the app so it can reconnect and pick up the ringing call. What differs is the signalling, and none of the big mobile SDKs speak plain SIP over WSS. Telnyx's native SDKs are MIT on both platforms but speak a Verto-derived JSON-RPC (`telnyx_rtc.invite`, `telnyx_rtc.attachCalls`, …) ([SocketMethod.kt](https://github.com/team-telnyx/telnyx-webrtc-android/blob/main/telnyx_rtc/src/main/java/com/telnyx/webrtc/sdk/model/SocketMethod.kt)). Twilio uses a proprietary TLS channel on 443 with closed binaries ([Twilio connectivity](https://www.twilio.com/docs/voice/sdks/network-connectivity-requirements)). Plivo abandoned its native SDKs and points developers to PJSIP or Linphone ([Plivo FAQ](https://docs.plivo.com/docs/faq/voice-api-and-SIP-trunking/sdk-and-endpoints)). SignalWire, the FreeSWITCH company, ships React Native targeting its own cloud, and its new alpha RN SDK says "No Android row is signed off" ([signalwire-react-native-unofficial](https://github.com/signalwire/signalwire-react-native-unofficial)). Where SIP over WSS does run on a phone, it runs as a JS or Dart UA on native WebRTC: jambonz uses JsSIP in React Native ([jambonz docs](https://docs.jambonz.org/sdks/webrtc)), and dart-sip-ua is a JsSIP port on flutter-webrtc, both MIT ([dart-sip-ua](https://github.com/flutter-webrtc/dart-sip-ua)). dart-sip-ua is the strongest precedent for our plan: someone already ported a JS SIP stack line by line into another managed language and ships it against FreeSWITCH-class PBXs.

Of the four layers, the outer two are borrowable. **Telnyx's `telnyx_common` is not separable as-is.** It declares `api project(':telnyx_rtc')`, and its core classes import `TelnyxClient`, `Call` and `PushMetaData` ([telnyx_common/build.gradle](https://github.com/team-telnyx/telnyx-webrtc-android/blob/main/telnyx_common/build.gradle), [TelnyxCommon.kt](https://github.com/team-telnyx/telnyx-webrtc-android/blob/main/telnyx_common/src/main/java/com/telnyx/webrtc/common/TelnyxCommon.kt)). Its shape is engine-agnostic and MIT, though: use cases for accept, reject, hold or swap and push answer, an FCM service, CallStyle notification services, a `phoneCall` foreground service and a Room call history. The `connection_service_app` sample's `TelecomCallService` imports no SDK types and is built on Jetpack core-telecom ([connection_service_app](https://github.com/team-telnyx/telnyx-webrtc-android/tree/main/samples/connection_service_app)), but it still consumes Verto socket events through its repository layer ([codex_plan_review.md](notes/codex_plan_review.md)). Codex suggests starting from Android's smaller Core-Telecom samples instead, which may cost less than transplanting both Telnyx layers ([Android Core-Telecom](https://developer.android.com/develop/connectivity/telecom/voip-app/telecom)). The practical design is a `CallEngine` interface in commonMain, implemented by our SIP UA, with the platform call manager and push code on the Android and iOS sides consuming it.

A Kotlin-specific iOS risk shows up in the JS-on-mobile precedents. An Apple forum report describes SIP.js sessions that worked when started manually but failed when driven through CallKit, an audio-session activation problem ([Apple Forums 691523](https://developer.apple.com/forums/thread/691523)). Another report describes JsSIP on react-native-webrtc with no remote audio on iOS ([react-native-webrtc discourse](https://react-native-webrtc.discourse.group/t/integrate-jssip-with-react-native-webrtc/284)). The usual CallKit pattern is to activate WebRTC audio only in `provider(_:didActivate:)` (standard practice, not fetched from Apple this session). That makes an early iOS audio and CallKit proof worth more than its size suggests.

## Incoming calls need push on both platforms and a park step FreeSWITCH lacks

On Android the endorsed wake path is an **FCM high-priority message**. It is an explicit exemption that lets the app start a foreground service from the background ([FGS background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)). The app then registers the call with Core-Telecom (`androidx.core:core-telecom:1.0.0`, `MANAGE_OWN_CALLS`, `CallsManager.addCall`), hosts it in a `phoneCall` foreground service, and must post a CallStyle notification **within 5 seconds** ([Core-Telecom](https://developer.android.com/develop/connectivity/telecom/voip-app/telecom)). FCM downgrades an app's high-priority messages if, over a 7-day window, they do not produce visible notifications. A downgraded message then makes the FGS start throw ([FCM priority](https://firebase.google.com/docs/cloud-messaging/android/message-priority)). So every call push, including calls cancelled before the app wakes, must surface something, such as a missed-call notification. Google's Doze table rates a battery-optimisation exemption as "Not Acceptable" for a calling app that can use FCM, allowing it only where Doze breaks core function, with "enterprise VOIP apps" named ([Doze & App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)). A permanent foreground-service WebSocket is therefore an internal or enterprise mode, not the public design. Google is also migrating FCM to a v2 `RemoteNotification` type. The Doze page calls v1 deprecated, but the FCM page still labels v2 pre-GA ([FCM v2](https://firebase.google.com/docs/cloud-messaging/send/v2-api)), so build on v1 high priority and watch v2.

On iOS a **PushKit VoIP push is the only reliable wake path**, and the rule is strict: report the call to CallKit before the push handler returns, or iOS 13+ terminates the app ([Apple: Responding to VoIP notifications](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit)). Repeated failures stop VoIP push delivery altogether, and developers report that only a reinstall restored it ([Apple Forums 764376](https://developer.apple.com/forums/thread/764376)). Apple tells apps to connect to the VoIP server in parallel with CallKit and to set `apns-expiration` to 0 or a few seconds. One consequence (inference) is that RFC 8599 "refresh your binding" pushes cannot be sent as VoIP pushes on iOS, so registrations need long expiries and a refresh whenever the app comes to the foreground.

The server side is where a WSS-only phone gets hard. When the app sleeps, its WebSocket dies, and the registration in mod_sofia points at a dead connection. **RFC 8599** defines the standard fix. The UA puts `pn-provider`, `pn-param` and `pn-prid` in its REGISTER Contact. On an incoming INVITE, the proxy pushes, parks the request, waits for the fresh REGISTER (measured at about 2 s after the push) and then forwards it ([RFC 8599](https://www.rfc-editor.org/rfc/rfc8599.html)). **FreeSWITCH has no native RFC 8599 support** ([SessionTalk](https://sessiontalk.io/blog/sip-push-notifications-asterisk-freeswitch)). The community `mod_apn` does push-then-wait, but it was built on Apple's legacy APNs protocol and lacks FCM ([freeswitch-PushNotificator](https://github.com/sem32/freeswitch-PushNotificator)). The proxy-tier alternatives each cost a new component and licence: OpenSIPS `mid_registrar` (GPL; a January 2026 user report of FCM lookups not firing is unresolved) ([OpenSIPS mid_registrar](https://opensips.org/docs/modules/3.6.x/mid_registrar.html), [OpenSIPS-Users 2026-01](https://opensips.org/pipermail/users/2026-January/049182.html)), Kamailio `tsilo` plus scripting ([tsilo](https://www.kamailio.org/docs/modules/stable/modules/tsilo.html)), and Flexisip's Push Gateway (AGPL or commercial) ([Flexisip Push Gateway](https://wiki.linphone.org/xwiki/wiki/public/view/Flexisip/Push%20Gateway/)). For a team that already routes calls in Lua on FreeSWITCH, the smallest design (inference) is this. Store the token, either through our own REST API or parsed from the Contact. When a mobile user is called, send an FCM v1 or APNs push carrying the call-id and caller ID, play ringback, wait up to ~25 s for a fresh `sofia::register`, bridge. If the caller hangs up first, tell the phone: on Android with a data push, on iOS over the connection the app opened after the VoIP push (Apple directs cancellation that way; a second VoIP push would itself have to show a call) ([Apple](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit)). Storing the token out-of-band avoids depending on mod_sofia preserving `pn-*` Contact parameters on WS registrations, which nobody has verified.

## Ranked options and the cheapest proof path to a reliable call

The owner's constraints (SIP, Kotlin, permissive licences, native, no native SIP libraries) remove most of the field before ranking starts. Verto via a Telnyx fork would be the fastest Android demo. It is ruled out because the owner chose SIP, and in any case it needs mod_verto plus protocol rework: stock mod_verto has no trickle `candidate` handler, no `ringing` and no `login_token` ([implementation_options.md](notes/implementation_options.md); [FreeSWITCH mod_verto](https://developer.signalwire.com/freeswitch/FreeSWITCH-Explained/Modules/mod_verto_3964934/)). baresip, PJSIP and Linphone are excluded by the no-native-SIP rule. Codex's plan review still suggested BSD baresip as a simpler alternative ([codex_plan_review.md](notes/codex_plan_review.md)), but that conflicts with the owner's decision. Flutter (dart-sip-ua) and React Native (sip.js plus react-native-webrtc) are permissive and proven, but they are not Kotlin.

| Rank | Option | Why | Main risk |
|---|---|---|---|
| **1** | **Grow our KMP SIP core along sip.js's `core/` layering; copy the uvp parser/message pieces and webphone-android's FreeSWITCH flows; media on webrtc-kmp** | Meets every constraint; server unchanged (mod_sofia WSS on :8443); one core for Android and iOS; the code we copy is MIT and the media stack Apache/BSD | We own transaction and dialog correctness; webrtc-kmp is stale (fork-and-bump fallback) |
| 2 | Run sip.js itself inside QuickJS (quickjs-kt, Apache-2.0, KMP incl. iOS, active ([quickjs-kt](https://github.com/dokar3/quickjs-kt))) behind a Kotlin SDH and WebSocket shim | Reuses the exact browser stack, so fewer SIP lines | No on-device precedent outside React Native; two-runtime debugging; RN users needed a custom SDH ([SIP.js group](https://groups.google.com/g/sip_js/c/ZUP0FEZpz44)); App Store rule 2.5.2 is likely fine for bundled JS, but only secondary sources say so |
| 3 | Fork webphone-android (MIT) for an Android-only first release, then port it to KMP | Fastest Android path with SIP over WSS | Untested against live FreeSWITCH; OkHttp/Android types; leads to a second rewrite for iOS |
| 4 | JAIN-SIP on Android only | Complete RFC 3261 layer, permissive | JVM-only, 2018 artifacts, broken WS client, no iOS path |

The proof sequence follows Codex's recommended order, extended with what the notes add about push and FreeSWITCH. Each gate is one attempt that either passes or changes the approach.

**Gate 0** is offline. Make the module KMP (add Android and iOS targets alongside `jvm()`), fix the open core defects (subscriberless SharedFlow drops, EOF propagation, REGISTER serialisation, Via-branch matching, Content-Length validation, structured Contact parsing), and add independent digest vectors and protocol fixtures.

**Gate 1** is a live REGISTER, scheduled refresh, reconnect and unregister against `wss://switch.voipappz.io:8443`, at parity with the browser's 300 s expiry ([codex_own_sip_core_review.md](notes/codex_own_sip_core_review.md)).

**Gate 2** is the critical one: an outbound call from a **physical Android phone** to an echo extension, with authenticated INVITE retry, ACK, two-way audio confirmed by `getStats`, and BYE. Use non-trickle gathering with a deadline and unmodified SDP.

**Gate 3** covers inbound INVITE (FreeSWITCH's offer must carry a fingerprint), the CANCEL/200 race (pending → 487; crossed 200 → ACK then BYE), RFC 4733 DTMF, and hold/resume re-INVITEs.

**Gate 4** is forced-TURN and Wi-Fi↔LTE tests, including whether FreeSWITCH accepts an ICE-restart re-INVITE.

**Gate 5** is Android incoming calls while killed: FCM high priority → `phoneCall` FGS → Core-Telecom → CallStyle within 5 s → WSS + REGISTER → bridged by the Lua push-park flow.

**Gate 6** is a minimal iOS call with CallKit-driven audio activation and a PushKit wake.

UI investment stays behind all of these.

To keep the epistemic status straight, the table below separates what was checked from what was inferred.

| Verified (read in code, repo metadata, RFCs or vendor docs) | Inference or estimate |
|---|---|
| No permissive KMP/iOS SIP-over-WSS UA found in our search; JAIN-SIP WS client hack; licences and activity listed for every candidate except Telnyx's WebRTC binary (unchecked) | That our hand-rolled UA reaches production reliability; no public precedent exists |
| sip.js sends no SDP modifiers, does no trickle, defaults to a 5 s gathering cap and does hold by direction change; FreeSWITCH does UDP-only ICE, has no TURN client and no trickle via mod_sofia | That webrtc-kmp SDP will negotiate with our FreeSWITCH unchanged (likely, unproven) |
| webrtc-kmp pins M125, last release 2025-09-07, has a common DtmfSender | That M125 is adequate for audio-only use |
| Current core handles binary frames, 423, redacted `toString`, explicit qop rejection, closed connections, Via-branch matching, Content-Length; Android target builds; 17 tests | That it works against the real switch (gate 1 not run); iOS build (needs a Mac) |
| sip.js line counts; uvp and webphone-android contents and defects | 5–7k Kotlin lines; 3–6 engineer-weeks to a reliable first call (researcher judgement) |
| Android FCM/FGS/Core-Telecom rules; iOS PushKit→CallKit rule; RFC 8599 mechanics; no native RFC 8599 in FreeSWITCH | That a Lua push-park flow in FreeSWITCH is sufficient, and that mod_sofia keeps `pn-*` params on WS |

## Conclusion

The decision is less risky than "write your own SIP stack" sounds. The problem is narrow: one server we control, one reliable transport that switches off the worst RFC 3261 timers, no trickle, and a media engine identical to the browser's. Proven MIT code (sip.js) also exists to port structure from, not just ideas. The real risk sits elsewhere: in state-machine edge cases nobody else has tested in Kotlin, in a wrapper dependency that has gone quiet for 14 months, and in incoming calls, which no client library can solve alone because FreeSWITCH needs a push-and-park flow it does not ship. That shifts the plan's centre of gravity. Gate 2 (a bare physical-device call) is the cheapest test of whether the whole approach holds. The Lua push-park flow is server work that should start in parallel rather than after the app, because it decides whether the phone ever rings when it is in a pocket.

Two things would change this recommendation. If Gate 2 shows that webrtc-kmp cannot produce SDP FreeSWITCH accepts without munging, the fork-and-bump fallback moves forward. If transaction and dialog bugs keep surfacing after Gate 3, running the unmodified sip.js core in QuickJS becomes the pragmatic retreat that still honours every owner constraint. Both are reversible because the `CallEngine` interface isolates them.
