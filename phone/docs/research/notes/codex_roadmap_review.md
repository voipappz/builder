**Verdict (inference): mobile first is sensible; keep the Rust desktop choice provisional.** Read-only review; no builds or live calls.

1. **Gate order — broadly right.** **Evidence:** [the plan](phone/docs/plan.md:17) puts Android audio before an early iOS proof; registration and iOS remain unproven. **Inference:** keep gates 0–3, arrange Mac/iPhone access now, and split gate 1 into the registration demo and renewal/reconnect acceptance. Bring push/Core-Telecom/CallKit feasibility alongside gate 3, before feature polish. Move secure storage before cold-start push, which must recover credentials. Retain forced-TURN/network-switching tests before a pilot and finished screens last.

2. **Desktop interoperability is a prerequisite.** **Evidence:** the [local Rust snapshot](eval/RustSIPPhone/README.md:246) supports UDP/TCP/TLS/WS/WSS but emits [G.711 RTP/AVP](eval/RustSIPPhone/src/sdp.rs:93), without WebRTC, DTLS-SRTP or ICE. [FreeSWITCH distinguishes signaling encryption from media encryption](https://developer.signalwire.com/freeswitch/users-and-endpoints/webrtc-sip/). **Inference:** registration could succeed while audio fails. Require proof of a reachable Sofia profile accepting plain RTP, or budget substantial media replacement. The actual switch configuration remains unverified. Rust offers existing calling features and compact distribution; compatibility still needs proof.

3. **Compare desktop reuse before committing.** **Evidence:** [Compose desktop targets JVM](https://kotlinlang.org/docs/multiplatform/supported-platforms.html); [webrtc-java](https://github.com/devopvoid/webrtc-java) supports Windows/macOS/Linux under Apache-2.0; [webrtc-kmp lacks desktop support](https://github.com/shepeliev/webrtc-kmp). **Inference:**

   | Alternative | Tradeoff against Rust |
   |---|---|
   | Compose + webrtc-java | Strongest reuse: shared SIP, call state and much UI. Needs separate media adapters, native-library packaging, bundled runtime and OS integration. |
   | Compose + [JCEF](https://github.com/chromiumembedded/java-cef) | Chromium WebRTC adds a JavaScript bridge, footprint and browser updates. Using sip.js would duplicate SIP again. |
   | Kotlin/Native | Shares logic, but needs desktop media bindings and UI integration beyond the established Compose/JVM path; likely more integration work. |

4. **Two implementations impose recurring cost.** **Inference:** SIP/dialog logic, features and applicable bug fixes require separate implementation and validation, plus Kotlin/Xcode and Cargo release pipelines. Limit drift now through a versioned protocol/behavior specification, independent digest/SDP/call-state vectors, one feature matrix and shared FreeSWITCH interoperability tests. Standardize account/domain, expiry, codec and DTMF settings; document unavoidable media-profile differences. One Kotlin codebase still requires platform-specific releases.

5. **Make demo acceptance explicit.** **Evidence:** [the screen](phone/shared/src/commonMain/kotlin/io/voipappz/phone/App.kt) immediately unregisters and assumes SIP domain equals WSS hostname. **Inference:** demo one needs provisioned credentials/domain, trusted TLS, authenticated REGISTER/200, matching Contact/expiry and unregister on a physical phone. Demo two needs a verified echo route, persistent request dispatch, authenticated INVITE/ACK/BYE, cancellation/timeouts, microphone permission/routing, bounded non-trickle ICE gathering and completed `localDescription`. Require audible echo, bidirectional media statistics and repeat-call cleanup. Budget maintenance of [webrtc-kmp’s M125 dependency](https://github.com/shepeliev/webrtc-kmp/blob/main/gradle/libs.versions.toml); browser-compatible SDP remains an interoperability hypothesis until tested.
